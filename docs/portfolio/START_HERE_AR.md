# ابدأ من هنا — فهم مشروع TBHM

TBHM هو Framework بيجمع مراحل مختلفة من Security Assessment داخل Workflow واحد: تحديد النطاق، اختيار المراحل، تنفيذ التحليلات، تجميع النتائج، التحقق من أدلة الثغرات المدعومة، ثم إنتاج تقارير ومخرجات قابلة للمراجعة.

**الفرق الأهم عن مجرد Scanner:** المشروع بيفرّق بين وجود إشارة محتملة على ثغرة، وبين ثغرة اتأكدت بأدلة وضوابط صحيحة. وكمان بيسجل المراحل اللي فشلت أو ما اشتغلتش؛ عشان `0 findings` ما تبقاش تلقائيًا معناها "الموقع آمن".

## أفهم المشروع بأي ترتيب؟

1. [نظرة عامة للـRecruiter والإنترفيو](RECRUITER_OVERVIEW.md): المشروع بيحل مشكلة إيه، وإيه اللي ممكن تعرضه من شغلك.
2. [المعمارية](ARCHITECTURE_WALKTHROUGH.md): البيانات بتدخل إزاي وتعدّي على الـDispatcher والـScanners والـVerifier والـReports.
3. [هيكل الملفات](MODULE_MAP.md): فين الـCore والـTests والـManifest والـDocs.
4. [التنفيذ العملي](WORKFLOWS.md): تثبيت Offline، فحص Source محلي، ثم مثال Target داخل Scope مصرح به.
5. [الدليل والتأكيد](PROOF_AND_FINDINGS.md): ليه الـHTTP 200 أو كلام الـLLM مش دليل كفاية على ثغرة.
6. [الذكاء الاصطناعي](LOCAL_AI.md): الـAI بيساعد في التحليل وترتيب الأولويات، لكنه مش صاحب قرار التحقق.
7. [الاختبارات](TESTING_AND_VALIDATION.md): إزاي تتأكد إن الـSource والـPhases والـPackage متوافقين.
8. [النشر](PUBLISHING_AND_PUSH_PROTECTION.md): مشكلة GH013 الحالية وإزاي تتعامل معاها بأمان.

## لازم تفرّق بين أربع حاجات

| المصطلح | المعنى |
| --- | --- |
| **Available phase** | الموديول مسجل؛ مش شرط نفذ فحص حقيقي |
| **Lead** | إشارة محتملة على ضعف محتاجة مراجعة |
| **Confirmed finding** | دليل مستوفٍ لشروط الـProof Contract المدعوم |
| **Coverage gap** | خطوة اتمنعت أو فشلت أو أدواتها ناقصة، وما ينفعش نعتبرها نتيجة نظيفة |

## الأرقام الموجودة في مراجعة النشر

- المراجعة المسجلة لنسخة النشر أظهرت **145 Phase Name** قابلة للحل إلى موديولات `run()`.
- تجهيز المصدر راجع **1,232 ملف** في الـManifest النهائي، مع **1,233 ملفًا** في الـStaging بما فيه الـManifest نفسه.
- التثبيت في Git Clone محلي نجح في اللوج المرفق.
- الـPush إلى GitHub **لم ينجح** بسبب GitHub Push Protection، رغم إنشاء الـRepository.

الأرقام دي أدلة على مرحلة معينة من البناء والمراجعة، **مش شهادة إن 145 Scanner اشتغلوا ضد Targets حقيقية**.

## طريقة تقديمه في البورتفوليو

قول إن هدف TBHM هو تحسين تنظيم فحوص الأمن وجودة الأدلة وتقليل الـFalse Positives، ثم اعرض مثالًا **محليًا ومُعاد إنتاجه فعليًا** باستخدام الموديولات اللي اختبرتها. ما تنسبش لنفسك كتابة أي جزء موروث من غير Git Commits أو أدلة. وما تنشرش Screenshots أو بيانات من فحوص العملاء.

الخطوة الأفضل بعد النشر: بناء **Demo تعليمي اصطناعي صغير** يوضح Observation → Negative Control → Verification → Report، مع اختبارات وتقرير من تشغيل فعلي. [خطة الديمو المقترحة](DEMO_PLAN.md).
