# Reviewed scenario learning and independent evaluation

The learning engine extends `core/ai_plane`: the existing `Store`, portable `AIHome`, `Audit`, `ProposalGate`, run observer and local Ollama client remain the entrypoints. SQLite remains authoritative. Scenario retrieval is a bounded SQL/lexical view, not a second database or opaque vector store. Legacy vectors continue to retrieve tool source; private legacy run chunks are excluded because they have no project authorization metadata.

## Five layers

| Layer | Executable implementation | Boundary |
|---|---|---|
| Scenario memory | `scenarios.py`, additive schema v6 | Imports always begin pending or quarantined; no imported reviewer/confirmation flags |
| Retrieval | `ScenarioMemory.retrieve/context` | Reviewed, unexpired, permitted train cases; same project or explicitly public shared cases; bounded candidates/results/context |
| Advisory reasoning | `Evaluator.prompt`, `LearningJobs.run_one`, existing local model client | Current labels withheld; prior text untrusted; structured citations; no execution/proof capability |
| Independent evaluation | `self_evaluation.py`, existing `quality_evaluation.py` | Operator-reviewed labels, immutable dataset manifest, project/root/family/fragment/near-duplicate split checks |
| Controlled improvement | `improvement.py`, existing `ProposalGate` | Compare active baseline, test exact candidate configuration, approve, promote and rollback retrieval settings only |

## Operator workflow

Every operation is a bounded JSON file with schema `tbhm.learning-operation/1`, `operation` and `project_id`. Commands work without a scan target:

```bash
./tbhm --ai-home /path/to/ai-home --ai-learning examples/learning-v425/01-ingest.json --approve-ai-learning
./tbhm --ai-home /path/to/ai-home --ai-learning examples/learning-v425/02-overview.json
```

Ingestion prints the sanitized `content_sha256`. Put that hash in `07-review-template.json`, replace the note with an actual independent review, and deliberately run it with `--approve-ai-learning`. The supplied example defaults to **inconclusive**. A program disposition such as duplicate/rejected does not change technical validity. A reviewed label is advisory data and cannot issue a confirmation receipt.

Retrieve or build the local searchable dashboard:

```bash
./tbhm --ai-home /path/to/ai-home --ai-learning examples/learning-v425/03-retrieve.json
./tbhm --ai-home /path/to/ai-home --ai-learning examples/learning-v425/04-dashboard.json --ai-learning-output /path/to/LEARNING.html
```

The dashboard is an escaped static operator artifact with no execution privileges. Output creation refuses links and overwrite. Use a fresh output filename when regenerating manually.

`--ai-observe --ai-scenario-context FILE` enables current-run capture when the permission file supplies an explicit project, scope, license and processing permission. Capture is bounded to 100 findings and creates pending sanitized scenarios only. It writes `LEARNING.html`/`learning_overview.json`, links them from `OPERATOR.html`, and completes before the orchestrator's final evidence seal. Capture failures are recorded as `learning_failed` events. The permission example must be edited for the actual owned lab before use. No private program report is fetched automatically.

Past closed runs can be imported with an `ingest_run` plan containing `run_database`, `run_id`, `vulnerability_class`, `test_objective`, `scope_reference`, `source_license`, `permission_reference`, `reuse_approved` and `split`. Input must be a bounded real SQLite findings table without an active WAL; supply a consistent backup for a live run. All imported labels remain untrusted pending independent review.

## Scenario data and provenance

Required fields are `scenario_id`, `run_id`, `project_id`, `scope_reference`, `vulnerability_class`, `test_objective`, `observation_summary`, `evidence`, `root_cause_id`, `source_license`, `permission_reference`, `reuse_approved`, and `split`. Evidence is an array of `{id, sha256, summary, kind}`; raw bodies, credentials and arbitrary local evidence paths are not part of the import schema.

Optional structured metadata covers target/environment, CWE/OWASP mappings, component/entrypoint, prerequisites, verification/proof observations, false-positive/missed-detection explanations, root cause, safe reproduction/remediation, model/retrieval versions, uncertainty, technology/input/sink/auth/dataflow, negative-control references, sensitivity, sharing, training permission, expiry, fixture/version families and source fingerprints. Stored schema/tool version and content hash are generated by TBHM. A scenario ID is immutable; use a new versioned ID for changed content.

Review records bind reviewer identity, technical validity, program outcome, decision, explanation and supplied evidence IDs to the exact sanitized content hash. Conflicting accepted technical labels quarantine the case. Raw/private-sensitive records and unknown authority fields are refused. Recognized secrets/PII are redacted before storage. Explicit reuse/license/processing declarations are operator attestations, not independent legal verification or a universal secret detector.

Reuse and training permission are separate. Only accepted, unexpired, reusable training-split cases with explicit training permission and a confirmed/refuted independent label enter `export_training`. Inconclusive cases can inform advice but cannot become binary training ground truth. The example has training permission disabled.

`revoke` removes a case from retrieval/training eligibility immediately and invalidates frozen evaluations and comparisons that reference it. Expiry has the same eligibility effect. Every export is rebuilt from current source reviews; `validate_training` with a `dataset` path compares the exported manifest and examples against current eligible data before an optional external training job. Old operator copies must be withdrawn separately. Revocation does not promise secure deletion from SQLite pages or third-party copies.

## Independent evaluation

Use `prediction` to record an operator-supplied advisory result, or `enqueue` followed by an explicitly approved `run_job` to invoke the configured local model. The strict response fields are `verdict`, `confidence`, `vulnerability_class`, `evidence_ids`, `scenario_ids`, `observed`, `unproven`, `benign_explanation`, `missing_control`, `safe_next_step`, and `falsifier`. Verdicts are positive/negative/inconclusive hypotheses. Unknown keys, proof/command fields and malformed values are rejected. Invalid citations are counted and demoted to abstention. A historical evidence citation uses `scenario_id:evidence_id`; current references use supplied evidence IDs.

`freeze` takes `evaluation_id` and unique reviewed `scenario_ids` in validation/test/regression/adversarial splits. It freezes scenario and review hashes before comparison. Never tune on held-out results or move their projects/root causes/families/fragments into training. Token similarity is a bounded near-duplicate heuristic, not a guarantee against all semantic leakage.

`evaluate` takes `evaluation_id` and `prediction_ids`. Every frozen case remains in the denominator, including missing predictions. Unknown ground-truth labels are separately reported. Reports retain TP/FP/TN/FN, positive/negative abstentions, conditional precision/recall/FPR/FNR, full-denominator bounds, coverage, Wilson intervals, citation validity, classification accuracy, Brier score, latency and measured process peak RAM when available. VRAM and unavailable measurements are null. Stages remain separate; triage is not discovery or proof verification.

The evaluation table retains separate baseline/candidate experiment IDs on the same dataset hash. `overview` exposes the latest result and configurations/jobs. The packaged benchmark reports eight synthetic retrieval queries and a deterministic surrogate workflow. It is explicitly **not** a real-model accuracy benchmark or representative field calibration.

## Approval, promotion and rollback

Only `feedback`, `k` and `max_chars` may be configured. `propose` requires a problem, supporting reviewed scenario IDs, baseline/candidate evaluation IDs and the exact candidate configuration. The baseline must match the active configuration; the candidate must match recorded prediction-job lineage. Missing predictions, fabricated citations, FP/FN/coverage/abstention regressions, absent labeled tasks, excess worker RAM or no measured improvement block promotion.

The existing `--ai-approve AI-PROP-XXXXXXXX` approves proposal intent. A separate approved `promote` operation activates the bounded configuration after rechecking reviews, comparison and active baseline. `rollback` restores the prior validated configuration and records audit history. No operation here applies patches, changes proof/scope authorization, replaces model weights or deploys a tuned model.

Pending jobs can be cancelled; failed/cancelled/interrupted jobs can be deliberately retried up to three claims. A cancellation event discards results from a running worker after the bounded model call returns. A crashed worker remains running until an explicit `recover` action marks it interrupted; it is not silently replayed. One running job per database and 32 outstanding per project provide backpressure. This synchronous local worker is deliberately separate from active scanning.

## Fine-tuning and limitations

Dataset preparation and revocation validation are implemented. Actual LoRA/QLoRA training and model promotion are deferred until explicitly approved data, compatible model licensing, suitable separate hardware, unchanged baseline/RAG comparisons and an independent held-out evaluation exist. There are no training frameworks or model weights in the core release. A model's agreement cannot bypass deterministic proof, authorization or safety boundaries.
